ファイル送信

multipart 形式でファイルを送信し、ブラウザーからサーバーへ転送された量を表示します。サーバー側の処理進捗を表すものではありません。

  1. UTF-8 の短いテキストを含む .txt ファイルを選択します。
  2. 送信し、転送中の進捗とサーバーからの検証結果を確認します。
  3. 形式エラー、120文字を超えるファイル名、1 MiB 超過の場合は、エラーを確認してファイルを選び直します。

テキストファイルを送信

UTF-8 の .txt を1件、最大1 MiBまで送信できます。ファイルの内容は検証後に保持せず、画面にも表示しません。

CSRF 不正・通信失敗同上403・HTTPエラー・通信断を通知。成功扱いにしない
  • enctype="multipart/form-data" と hx-encoding でファイルを含むフォームを送ります。CSRF は通常フォームのトークンと htmx の同一オリジン用ヘッダーで検証します。
  • htmx の要求開始時に対象 XHR の upload へ標準の progress イベントを登録し、送信済み量を <progress> に反映します。送信イベントだけを購読するため応答受信の進捗とは混ざりません。100% はブラウザーが本文を送り終えた意味であり、サーバー処理の完了を示しません。
  • サーバーは件数、1 MiB の容量、120文字のファイル名、拡張子と UTF-8 の実データを検証します。ブラウザーの accept と申告 MIME 型だけでは判定しません。入力内容は出力せず、ファイル名はパス部分を除いてエスケープ表示します。
  • 検証後にアプリケーションの状態としては保存しません。サーブレットが要求処理用に作成した一時データは要求終了時にクリーンアップされます。ファイルのプレビュー、実行、恒久保存は行いません。
  • 通常フォームの検証エラーでブラウザーのファイル選択を復元することはできません。再選択してください。別例「Preserving File Inputs after Form Errors」で htmx 差し替え時の保持を扱います。

状態・制約

固定データやセッション状態は使いません。要求は1ファイル、1 MiBまでです。1 MiB はファイル本体の上限で、multipart の境界などを含む要求全体にも 1100 KiB の上限があります。ファイル内容は UTF-8 テキストで、NUL などの制御文字を含まない必要があります。

送信中の通信断や30秒のタイムアウトでは成功と見なしません。入力ファイルを選び直し、必要ならページを再読み込みして再試行してください。この例ではサーバー側の長時間処理を行いません。

公式例との差分・出典

htmx 公式 File Upload の multipart 送信と進捗表示を参考にしています。送信と応答受信の進捗を混同しないよう、公式例の htmx:xhr:progress ではなく対象 XHR の upload に標準 progress リスナーを登録します。公式例の Hyperscript とインライン JavaScript は使わず、外部 JavaScript、サーバー検証、容量上限、CSRF、通常フォーム、要求後の破棄を加えています。追加依存はありません。
