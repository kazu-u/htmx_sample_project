仕組みと通信

Controller は送信された段階だけを検証し、セッション内の下書きを更新します。htmx は JSON を組み立てず、返された HTML で申請フォーム領域を置き換えます。

すべて /examples/multi-step-form 配下。htmx 使用時は #application-wizard を更新

  • 各 POST は CSRF トークンを検証します。申請者と出張内容を別段階で検証し、次の段階へ進む前に不備を422で返します。
  • 前段階へ戻る操作も POST で、入力中の値を下書きに保持します。段階を飛ばした要求や古い revision は409で拒否します。
  • htmx 使用時は HTML 断片、通常フォームでは成功後にページ全体を表示します。エラー時は入力値と項目別エラーを残します。
  • 画面内の戻る・次へを提供します。段階をURLやブラウザー履歴へ記録しないため、ブラウザー履歴による段階移動は行いません。

異常系と復帰

申請者を空欄にする、行き先を空欄にする、終了日を開始日より前にするなどで422になります。値を直して再送信できます。通信断・HTTPエラー・10秒のタイムアウトでは共通通知を表示し、現在のフォームを残します。

別タブで先に段階を進めてから古いタブを送信すると409になります。ページを再読み込みして最新状態を確認してください。20分のセッション期限後は、CSRF トークンも失効して更新要求が403になることがあります。ページを再読み込みすると新しい空のフォームから始まります。

状態の寿命と制約

下書きはセッションごとに1件で、20分の無通信またはサーバー再起動で消えます。明示的なリセットでも消去できます。ブラウザーや別セッションとは共有しません。サンプルは架空の内容だけを入力してください。

確定操作は完了画面へ遷移するだけで、DB・外部 API・業務登録は行いません。依存追加はありません。外部公開には認証・認可・HTTPS・負荷対策が必要です。サーバー全体のセッションは100個までで、上限到達時は503です。

公式例との差分・出典

htmx 公式の Validation と Progressive Enhancement の考え方を参考に、複数段階のサーバー検証・セッション内下書き・確認・リセットをこのプロジェクト向けに構成しました。公式例の逐語転記ではなく、標準フォームと CSRF 保護を維持しています。
