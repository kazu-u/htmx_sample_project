# Copilot の読み込み・権限の確認

## 1. 対象と現在の状態

VS Code の Copilot（Agent Host）と Local の両方を使う。
設定定義は VS Code 1.143.1 / 同梱 GitHub Copilot 0.71.0 で確認した。バージョン更新で UI・適用範囲が変わる場合は再確認する。

| 項目 | 状態 |
| --- | --- |
| 共通指示 | [copilot-instructions.md](../.github/copilot-instructions.md) を配置済み |
| ワークスペース設定 | [settings.json](../.vscode/settings.json) を配置済み、JSON の構文とインストール済みの設定定義を確認 |
| レビュー用設定 | [independent-reviewer.agent.md](../.github/agents/independent-reviewer.agent.md) を配置済み。読み取り・検索のみを使うよう指示 |
| Copilot / Local での指示の自動読み込み | 新規セッションでの画面確認は未実施 |
| コマンド・外部操作の承認表示 | 各実行方式での実動作確認は未実施 |
| レビュー用の OS レベルのツール制限 | 提供しない。サブエージェントへの運用指示で変更・コマンド・外部操作を避ける |

ファイルの存在・内容検査と、ランタイムでの適用確認を区別する。
設定を書いただけでは、現在の会話の権限や既存の承認状態が切り替わったとは判断しない。

## 2. 設定したもの

| 設定 | 目的・制約 |
| --- | --- |
| `github.copilot.chat.codeGeneration.useInstructionFiles: true` | Local で共通指示の利用を明示。Copilot 側は対応する独自の探索規則を使う |
| `chat.permissions.default: "default"` | Local の新規セッションを標準の承認設定で開始する |
| `chat.defaultConfiguration` の `interactive` / `manual` | Copilot の新規セッションを対話・手動承認で開始する |
| `chat.tools.global.autoApprove: false` | 全ツール一括の自動承認を無効にする |
| `chat.tools.terminal.enableAutoApprove: false` | ターミナルコマンドは読み取りも含め原則承認を求める |
| `chat.tools.urls.autoApprove` の `"*": false` | URL の要求・応答の自動承認を避ける。ネットワークを遮断する設定ではない |
| `chat.tools.eligibleForAutoApproval` の `fetch` / `runTask: false` | 当該ツールの自動承認を許可しない。全 MCP ツールを網羅する設定ではない |

`false` は原則「承認を求める」であり「実行を禁止する」ではない。
手動承認でも通常のソース編集は可能で、読み取り専用にはならない。
既存セッションの選択、過去に保存した承認、ユーザー・組織ポリシー、ツールの種類により、実際の動作は別途確認する。

## 3. 利用者が画面で確認する手順

### A. ワークスペースと承認状態

1. このプロジェクトのルートフォルダーを VS Code で開く。開発用の Folder 分離を使い、Worktree は今回の確認には使わない。
2. 必要に応じて **Developer: Reload Window** を実行する。未保存の編集や実行中タスクを先に確認する。
3. 設定画面の Workspace タブで、上記設定に「不明な設定」「このスコープでは適用できない」等の警告がないことを確認する。
4. Copilot と Local それぞれで新規チャットを作り、**Manual permissions** または該当する標準承認モードを確認する。**Allow all / Autopilot** にしない。
5. **Chat: Manage Tool Approval** で、特に GitHub 更新・MCP・ターミナルの保存済み承認を確認し、包括的な自動承認を解除する。
6. 保存済み承認を一括解除する **Chat: Reset Tool Confirmations** は他プロジェクトにも影響しうるため、必要性を確認して利用者自身が実行する。今回の設定で勝手に実行しない。

実行方式によって表示・対応範囲が異なる。設定の警告や意図しない実行があれば、確認済みとは扱わず、表示名・実行方式・ツール名を記録する。

### B. 共通指示の読み込み

Copilot と Local のそれぞれで、次の操作を行う。

1. 対象の実行方式を選び、**Chat: Open Customizations** の Instructions に共通指示ファイルが表示されるか確認する。これは「発見」の確認であり、実際の適用確認とは分ける。
2. 新規チャットを開く。現在の会話を継続せず、指示ファイルを手動添付しない。
3. 次の質問を送る。

   > このプロジェクトで、データ保存、画面の生成、追加依存、PR 前レビューについて従う制約を短く説明してください。変更やコマンド実行はしないでください。

4. 応答の **References** などの参照表示で、共通指示が使われたことを確認する。必要なら **Agent Debug Logs** で探索・添付を確認する。UI が異なる場合は、その実行方式で提供される診断表示を使う。
5. DB 不使用、HTML / Thymeleaf の断片、依存追加の制約、サブエージェントによる PR 前レビューが説明されるか確認する。

ファイルを直接読むツール呼び出しや、README から内容を推測できたというだけでは、自動添付の証拠にしない。
参照・診断表示がなく確認できなければ「未確認」と記録する。診断ログは認証情報・会話を含む可能性があるため、丸ごと共有・コミットしない。

### C. 開発セッションの承認

レビュー用エージェントではなく、通常の開発用エージェントで確認する。

1. 新規チャットで、読み取りだけの `git status --short` を実行するよう依頼する。
2. コマンド実行前に承認が求められることを確認する。承認は1回限りとし、包括的な許可を保存しない。
3. 外部取得については、公式の `https://htmx.org/` を読み取り専用で取得するよう依頼し、対応する承認表示を確認する。
4. GitHub の書き込みや秘密ファイルの操作を、動作確認のために試さない。GitHub 更新・MCP の自動承認はツール承認画面で確認する。

承認なしで実行された場合、理由を調べるまでは「承認制御確認済み」としない。
`git status` は単なる非破壊の確認用であり、全コマンド・全 MCP ツールへの制御を証明しない。

### D. レビューサブエージェント

PR 前の通常フローは、実装セッションから Independent Reviewer サブエージェントを呼び出します。利用者が新規チャットを用意する必要はありません。

1. レビュー担当に正確なパッチ本文、目的、要件 ID、レビュー回数を渡します。実装会話や過去のレビュー結果は渡しません。
2. エージェント定義に従い、ファイル読み取り・検索だけを使い、編集・コマンド・Git 操作・外部サービス操作は行わないよう依頼します。
3. ツールが見えることだけで中止せず、禁止操作のツールを呼び出さないでレビューを続けます。読み取り・検索ができない場合は制約とレビューできた範囲を報告します。
4. Independent Reviewer が利用不能・開始前停止・未完了なら、利用者に切り替えを確認せず、新しい組み込み `code-review` サブエージェントへ自動切り替えします。同じ読み取り専用条件と正確な差分を渡し、停止した担当との会話や過去結果は渡しません。
5. レビュー結果を優先度ごとの対応に従って処理します。修正後は関連テストを実行し、更新した全差分を新しいレビューサブエージェントへ渡します。停止した試行は完了に数えず、担当の切り替えと確認範囲を PR に記録します。
6. 代替担当でも未完了なら、パッチの直接添付等を試します。それでも完了できない場合のみ、PR 作成を止めて利用者に相談します。詳細は [レビュー方針](review-policy.md#レビュアーの自動切り替え) を参照してください。

エージェント定義は OS レベルのサンドボックスではありません。読み取り可能なファイルや、実行環境に存在する他のツールへの技術的アクセスを遮断するものではないため、レビュー担当への操作禁止指示と実際のツール呼び出しを区別して扱います。

## 4. 今回変更していないもの

- ユーザー全体の設定、既存セッションの権限選択、保存済みのツール承認
- 秘密ファイル・設定ファイルの編集に対する個別承認。`chat.tools.edits.autoApprove` は確認した版でアプリケーションスコープのため、ワークスペース設定へは追加していない
- 実験段階の Windows サンドボックス、OS のアクセス制御、ネットワーク遮断
- GitHub のブランチ保護・ルールセット、必須 CI、PR レビュー承認ルール
- 自動レビュー実行スクリプト、OS レベルのサンドボックス、実行環境での承認 UI

秘密ファイルの編集承認は、ユーザー設定へ影響することを合意してから設定する。
承認設定は秘密ファイルの読み取り禁止にはならないため、秘密情報をワークスペースへ置かない運用も必要。
GitHub の保護は別レイヤーであり、リポジトリのプラン・ルールの対応状況と、人のレビュー体制を確認してから設定する。
