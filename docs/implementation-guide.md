# 実装・解説ガイド

## 1. 新人向け説明の基本

想定読者は Java の変数・条件分岐・メソッド・クラスを理解している方です。
Spring MVC、Thymeleaf、HTTP、htmx の用語は、最初に登場する箇所で簡潔に説明します。
Java の入門書を丸ごと再現するのではなく、画面とコードを行き来して理解できる説明を目指します。

### 最初に説明する用語

| 用語 | このプロジェクトでの意味 |
| --- | --- |
| Controller | URL と HTTP メソッドに応じて処理を受け付け、表示する HTML を決める Java クラス |
| Model | HTML テンプレートへ値を渡す入れ物 |
| Thymeleaf | HTML テンプレートにサーバーの値を埋め込む仕組み |
| フラグメント | 一覧の行やフォームなど、再利用・部分更新する HTML のまとまり |
| htmx | HTML 属性で通信の契機・送信先・更新先などを指定できるライブラリ |
| CSRF トークン | 意図しないサイトからの更新要求を防ぐため、サーバーが検証する値 |

## 2. コードに付ける説明

「各プログラムに説明を付ける」は、全行にコメントを書くという意味ではありません。
読み手が責務とデータの流れを理解できる、短い日本語説明を置きます。

| 対象 | 説明すること |
| --- | --- |
| Java クラス・record | 何のための型か。状態を持つ場合は、その範囲と寿命 |
| Controller のハンドラー | 対応する画面操作、受け取る入力、ページ全体か断片か |
| フォーム | 各入力値の意味、制約が必要な理由 |
| 状態を操作する処理 | 初期化、更新、競合対策、失効時の扱い |
| HTML テンプレート | ページの役割、主要なフラグメントと差し替え先 |
| JavaScript | HTML 属性だけでは不足する理由、購読するイベントと副作用 |
| CSS | 処理中表示・動きの抑制など、学習上の意味がある箇所 |
| 設定 | 非デフォルト設定を採用する理由と影響 |
| テスト | テスト名だけでは分かりにくい前提条件や特殊なケース |

型・メソッドは必要に応じて Javadoc を使い、HTML / CSS / JavaScript は適切なコメント形式を使います。
自明な getter、代入、ループの一行ごとの説明は不要です。
Spring Boot が自動設定することと、本プロジェクトが明示的に設定することを区別して説明します。

## 3. 各サンプル画面に付ける説明

画面には、デモだけでなく次の内容を日本語で用意します。
折りたたみ等で読みやすくしても、重要な制約・エラーは隠しません。

1. **何ができるか** — 利用場面と学習目標
2. **操作手順** — 最初に押すボタン、入力例、確認する変化
3. **通信と差し替え** — 操作、HTTP メソッド、URL、応答、画面更新先の対応表
4. **主要コードの読み方** — Controller、テンプレート、`hx-*` 属性への案内
5. **状態の扱い** — 固定データかセッション単位か、初期化方法と消えるタイミング
6. **異常系の試し方** — 不正入力、対象なし、通信失敗などと期待結果
7. **安全性と操作性** — CSRF、入力検証、処理中、キーボード、フォーカス
8. **制約と本番利用時の注意** — 簡略化、上限、未対応事項
9. **公式例との関係** — 出典 URL、参考にした考え方、実装の差と理由

コードの抜粋を画面に載せる場合、HTML として実行されないようにエスケープします。
掲載箇所の名前・内容は実コードと同期し、実在しないファイルや存在しない機能を案内しません。

### 通信表の例

以下は「クリックで編集」の設計例です。実装・確認後の仕様ではありません。

| 操作 | メソッド / URL の例 | サーバーの役割 | 応答と更新先 |
| --- | --- | --- | --- |
| ページを開く | `GET /examples/click-to-edit` | 初期状態を表示 | 200、ページ全体 |
| 編集を押す | `GET /examples/click-to-edit/contact/edit` | 現在値入りのフォームを作る | 200、連絡先領域を置換 |
| 保存する | `POST /examples/click-to-edit/contact` | CSRF 検証後に入力検証・更新 | 200、連絡先の表示を置換 |
| 保存時に入力エラー | 同上 | 更新せず入力とエラーを返す | 422、編集フォームを置換 |
| キャンセル | `GET /examples/click-to-edit/contact` | 保存済みの値を表示 | 200、連絡先領域を置換 |
| 初期状態に戻す | `POST /examples/click-to-edit/reset` | セッション内の対象例を初期化 | 200、初期表示を反映 |

### htmx 属性の説明例

| 属性 | 説明する観点 |
| --- | --- |
| `hx-get` / `hx-post` 等 | どの操作で、どの URL に、何を送るか |
| `hx-trigger` | いつ送るか。イベント・遅延・発火回数の意味 |
| `hx-target` | どの領域を更新するか。対象が一意に決まるか |
| `hx-swap` | 中身の置換か、要素ごとの置換か、追記か |
| `hx-indicator` | 通信中であることをどこに表示するか |
| `hx-disabled-elt` | 通信中にどの操作を止めるか |
| `hx-swap-oob` | 主な更新先以外をなぜ同時に更新するか |

属性を使わない例まで、機械的にすべてを説明する必要はありません。
標準の動作に依存する場合は、その標準が何かを説明します。

## 4. 実装の単位と順序

### 基盤を用意する

1. JDK の提供元、固定バージョン、対応する Spring Boot / Maven の組み合わせを確認する。
2. 最小の Maven プロジェクトと Wrapper、ループバックでの起動設定を用意する。
3. Thymeleaf の共通画面、ローカル htmx / CSS / JavaScript を配置する。
4. 認証なし・CSRF 有効の Security 設定、トークン送信、エラー表示を用意する。
5. htmx の安全設定と CSP をそろえ、簡単な取得・更新で動作を確認する。
6. 実際に確認できた環境構築・起動・テスト手順を README に記載する。

### 「クリックで編集」を一通り仕上げる

1. 架空の連絡先データをセッション単位で扱う。
2. 表示、編集フォーム、保存、キャンセル、初期化を実装する。
3. サーバー側の入力検証と、422 でのフォーム再表示を実装する。
4. 処理中表示、入力保持、フォーカス、通信失敗からの復帰を確認する。
5. 日本語解説と通信表を付け、テストと手動確認をそろえる。
6. 分かりにくい設計・説明がないか確認してから、次の例に進む。

後続の例でも、デモの正常動作だけを先に量産しません。
共通のイベント処理は重複登録を避け、断片更新でイベントが多重に発火しないようにします。

## 5. テスト・動作確認

テストは既存の Spring Boot / Spring Security の仕組みを優先します。
Controller とテンプレートの検証は、必要な設定を含む MockMvc 等で行います。
ブラウザーの自動化ツールは初期必須依存にせず、手動で確認した手順と結果を残します。
自動化が必要になった場合に、導入理由と対象を決めます。

### 自動テストで確認すること

- ページ全体と断片が期待する HTML・ステータスで返る。
- 更新入力の正常系・境界値・不正値で、状態と応答が正しい。
- 不正な入力では状態が変わらず、入力値とエラーが返る。
- 存在しない対象が 404 などの想定した応答になる。
- CSRF トークンなし・不正なトークンの更新が 403 で拒否される。
- 必要な全更新メソッドで、正しいトークン付き更新が成功する。
- タグやスクリプトに見える入力が、実行可能な HTML として出力されない。
- 異なるセッションのデータが混ざらず、初期化が他セッションへ影響しない。
- 状態・ファイル・ジョブに上限がある例は、その境界と後始末も検証する。

### ブラウザーで確認すること

- 実際の htmx リクエストと差し替え先が通信表と一致する。
- 422 のフォームが表示され、それ以外のエラーも利用者に通知される。
- 二重クリック、素早い連続操作、遅い応答、通信断でも表示が破綻しない。
- 入力エラー時に入力が残り、修正して再送信できる。
- キーボードだけで主要操作ができ、差し替え後のフォーカスが適切である。
- 処理中と完了・失敗が、色以外でも分かる。
- モバイル幅、動きを減らす設定、必要な読み上げ通知を確認する。
- CSP 違反、JavaScript エラー、意図しない外部リクエストがない。
- セッション失効後、再読み込みなどで復帰できる。
- 履歴や非 htmx の代替を扱う例は、直接アクセス・戻る・進む・JavaScript 無効も確認する。

サーバー側テストだけで、htmx の画面差し替えが動作したとは判定しません。
テストに通っても未確認のブラウザーや入力は、未確認として記録します。

## 6. 一つのサンプルの完了条件

- [ ] 学習目標と対象範囲が明確で、台帳の項目に対応している。
- [ ] 正常系だけでなく、その例に関係する入力エラー・通信失敗を処理している。
- [ ] CSRF・エスケープ・入力検証・リソース上限などの共通方針に従っている。
- [ ] 状態の範囲、寿命、初期化方法が説明されている。
- [ ] 日本語のコード説明と画面上の解説があり、通信を追える。
- [ ] 公式例との差分、出典、追加依存、制約が記録されている。
- [ ] 対象テストとブラウザー確認を実施し、実行結果・確認環境を記録している。
- [ ] 関連ドキュメントと台帳を更新している。

このガイド自体は実装済み機能の証明ではなく、今後の実装・レビューで使う基準です。

## 7. PR 作成前の独立レビュー

サンプルの完了条件の確認とは別に、PR 作成前に [レビュー方針](review-policy.md) に従って実装とは別のレビューサブエージェントで最新差分をレビューします。利用者がレビュー専用チャットを別途作る必要はありません。
実装側から渡すのは、レビュー対象の正確な差分、変更目的1〜2行、要件 ID、レビュー回数だけです。実装の経緯・会話・コミット履歴・過去のレビュー結果は渡しません。
レビュー後の修正はテストを再実行し、更新した全差分を新しいサブエージェントで再レビューします。指摘の対応・保留理由と CI の未実行を含む検証結果を PR に記録し、マージは人が承認します。
