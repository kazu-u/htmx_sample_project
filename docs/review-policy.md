# レビュー方針

## 1. 目的と基本ルール

PR を作成する前に、実装・テストとは別のサブエージェントで最新差分を必ず1回以上レビューします。
文書のみの変更も対象です。[Dependabot の PR の例外](#7-dependabot-の-pr-の例外)だけは更新内容に応じて省略できます。
AI レビューは補助であり、マージの承認は人が行います。

- 実装した AI は、自分の変更を自分でレビューしない。
- 実装側のテスト・動作確認は行うが、それを独立レビューとは数えない。
- 利用者がレビュー専用のチャットを作る必要はない。実装セッションから独立したサブエージェント呼び出しを使う。
- レビュアーには実装の経緯を渡さず、差分とリポジトリの内容に基づいて判断させる。
- 採用する指摘には根拠と失敗シナリオを必要とする。
- P0 は修正する。P1 の保留と指摘の棄却は利用者の判断を得る。
- P2 は実装側が影響・修正コストを評価し、修正するか理由を PR に記録して受け入れる。

## 3. レビュアーセッション

### 渡すもの

- レビュー対象の正確な差分そのもの（依頼文への添付・パッチ本文など、サブエージェントが実際に読める方法で渡す）
- リポジトリ内容をファイル読み取り・検索で確認できる状態
- 変更の目的を1〜2行
- 対応する要件 ID（[要件一覧](requirements.md) の `F-xx`）
- レビュー回数（第 N 回）

「現在の PR / ブランチ差分を確認してください」と伝えるだけでは、差分を渡したことになりません。レビュー対象の差分を依頼文に含めるか、サブエージェントが確実に読める添付として渡します。共有できない一時パスだけを渡さず、読めない場合は差分を依頼文に含める等の方法へ切り替えます。

### 渡さないもの

- 実装の経緯、迷い、検討過程、実装セッションの会話
- コミット履歴とコミットメッセージ。`git log` を使わせない
- 過去回のレビュー結果。修正後は新しいレビューサブエージェントに最新差分を渡して判断させる

### 権限と実行方法

- レビュー担当は読み取り・検索だけを使う。ファイル変更、コマンド実行、Git 操作、コミット、プッシュ、外部サービス操作、レビューの再委譲はしない。
- 禁止操作のツールが実行環境に見える場合も、それらを呼び出さない。ツールの存在だけを理由に停止せず、実際に読み取り・検索ができない場合は可能な範囲を報告する。
- レビュアー自身に `git diff` 等で対象差分を生成させない。実装側が正確な差分を用意して渡す。
- レビュアーはテストを実行しない。コードを読んでテスト範囲を評価し、テスト未実行を明記する。
- サブエージェント呼び出しを実装から独立したレビューとして扱う。利用者が別チャットを作る必要はない。

### レビュアーの自動切り替え

Independent Reviewer の利用不能、開始前の停止、対象差分を確認できずレビュー未完了となった場合は、実装側が新しい組み込み `code-review` サブエージェントへ切り替えます。ツールの存在だけを理由とする停止も対象です。同じカスタムレビュアーの起動を繰り返したり、利用者に切り替えの許可や別チャット・環境の用意を求めたりしません。この代替利用は本方針で事前承認された通常運用です。

- 代替担当にも、上記と同じ読み取り・検索のみの制約と、本書の観点・優先度・出力形式を依頼文で明示する。編集・コマンド・Git 操作・履歴参照・外部操作・テスト実行・再委譲は許可しない。
- 正確な最新差分、リポジトリ内容、目的1〜2行、要件 ID、レビュー回数だけを渡す。停止した担当との会話や過去のレビュー結果は渡さない。
- 対象差分全体の確認と結果の報告をもって完了とする。停止・未完了の試行を、指摘なしや完了回数に数えない。
- 代替担当の結果も同じ P0 / P1 / P2 の対応に従う。担当の切り替えは指摘の棄却・保留やレビュー省略を許可するものではない。
- 切り替えの発生・担当・完了回数・確認範囲と制約は PR に記録する。カスタム定義の再読み込み・実行環境の修復まで成功したとは報告しない。
- 代替担当でも未完了の場合は、パッチ本文の直接添付など不足を補う方法を試す。それでも対象差分全体をレビューできなければ PR 作成を止め、未確認範囲と制約を利用者へ相談する。

この切り替えは運用ルールであり、実行環境の承認 UI・ツール権限・上位の制約を変更または迂回するものではありません。指示の読み込みや担当の挙動を技術的に保証するものでもありません。

## 4. レビュー観点

このプロジェクトの実際の仕様に基づいて評価します。
別プロジェクトにあるファイル名・技術要素が存在することを前提にしません。

| 観点 | 主な確認内容 | 現在の参照先 |
| --- | --- | --- |
| セキュリティ | 認証なしという公開範囲の意図、各エンドポイントの扱い、CSRF、入力検証、インジェクション、機密情報の露出、同一オリジン制限、ファイル・メモリ・処理の上限 | [プロジェクト方針・設計](project-policy.md) |
| テスト | 変更に対応する検証、境界値の両側と境界値、主要分岐、セッション分離、固定可能な時刻、根拠のないテスト削除・弱体化 | [実装・解説ガイド](implementation-guide.md) |
| 設計 | 構成・責務・規約との整合、不要な抽象化、依存追加の ADR・ライセンス、DB 不使用、状態の寿命と競合 | [プロジェクト方針・設計](project-policy.md) |
| 契約・文書 | HTTP メソッド・URL・ステータス・HTML 断片と画面の整合、解説と実装の一致、仕様変更時の文書更新 | [実装・解説ガイド](implementation-guide.md)、[サンプル台帳](sample-catalog.md) |

骨抜きテスト（常に成功するモック、根拠のない条件付きスキップ、検証のないテスト）も確認します。
クライアントから JSON 等を受け取る機能が追加された場合、その入力も検証対象です。
認証・認可・トークンを扱う箇所では、必要な成功・拒否パターンのテストを確認します。認証なしの現構成に、ログインやロールの機能を勝手に要求しません。

現時点では TOTP、収集機能、DB・マイグレーション、JSON レポートスキーマは対象にありません。
それらの導入を本書が承認するわけではありません。追加する場合は要件・対象範囲・関連文書を先に見直し、その後にレビュー観点へ加えます。

## 5. 優先度と指摘の形式

| 優先度 | 意味 | 対応 |
| --- | --- | --- |
| P0 必須修正 | セキュリティ、データ破壊、機能の誤り、絶対ルール違反。骨抜きテスト、認証・認可・トークン周りの必要なテスト欠落、禁止したデータの収集、未承認の対象外機能、ADR なしの依存追加も含む | 必ず修正する。妥当性が不明なら利用者に確認し、解決するまで PR を作成しない |
| P1 推奨修正 | 深刻なバグの恐れ、境界値や主要分岐のテスト不足、設計方針からの逸脱、仕様変更に伴う文書の更新漏れ | 修正する。合理的な理由でスキップする場合は人の承認と PR への理由記載が必要 |
| P2 軽微 | スタイル、命名、影響の限られた改善 | 実装側が影響と修正コストを評価して修正または受け入れ、未修正理由を PR に記録する。継続管理が必要な場合に Issue を起票する |

- P0 / P1 は「どの入力・状態で、どう失敗するか」を具体的に書ける指摘に限る。書けない場合は P2 とする。
- 各指摘に確信度「確実 / 可能性あり」を付ける。「可能性あり」の P0 は人が確認する。
- 未承認の対象外機能には、たとえば端末制御・常駐化など、サンプルの目的にない機能を含む。
- DB 導入が承認された将来には、破壊的マイグレーションや適用済みファイルの編集も P0 の対象とする。

各指摘には、優先度、確信度、対象ファイル・行、根拠となる要件・方針、具体的な失敗シナリオ、影響を記載します。
P2 のスタイル指摘では、実害を捏造せず改善理由を書きます。P1 の保留と指摘の棄却は利用者が判断します。P2 の受け入れは実装側が影響・修正コストを評価し、理由を記録します。

## 6. PR までの流れ

1. 実装側が変更に対応するローカルテスト・ブラウザー確認と文書更新を行う。
2. 実装側が最新差分のパッチを作成し、対象変更を過不足なく含むことを確認する。
3. 要件 ID、目的、レビュー回数と差分だけを、新しいレビューサブエージェントに渡す。会話の経緯・コミット履歴・過去結果は渡さない。
4. サブエージェントが読み取り・検索でレビューし、P0 / P1 / P2 の指摘、根拠、失敗シナリオ、確信度を報告する。
5. P0 は必ず修正する。P1 は原則修正し、保留する場合は利用者の判断を得て理由を PR に記録する。P2 は影響とコストを見て修正または受け入れ、対応を PR に記録する。
6. 指摘を修正した場合は関連テストを再実行し、更新後の全差分を新しいレビューサブエージェントで再レビューする。最終差分をレビュー済みにする。
7. ローカル検証、未実施の CI、レビュー結果と対応を PR に記載する。
8. レビュー完了後にコミットし、PR を作成する。マージの承認は人が行う。

P0 が未解決、P1 の保留に利用者の判断がない、または最終差分に未レビューの変更が残る場合は PR を作成しません。
レビュー結果や対応記録は保持しますが、次のレビュー担当には過去結果を渡しません。

## 7. Dependabot の PR の例外

Dependabot の PR は、実装した AI がいない自動生成の PR です。
毎週の更新すべてに AI レビューを必須とするのではなく、**上から順に判定し、最初に当てはまる行**を適用します。

| 順 | 更新の種類 | AI レビュー | 理由 |
| --- | --- | --- | --- |
| 1 | 版の種類にかかわらず、Spring Boot、Java（将来 Docker を採用する場合はそのベースイメージを含む）、Maven / Maven Wrapper、認証・暗号・トークン・DB に関わる依存 | 必須 | 実行環境、ビルド、認証、データに影響するため |
| 2 | メジャー更新。`0.x` のマイナー更新、GitHub Actions のメジャー更新も含む | 必須 | 互換性のない変更を含みうるため |
| 3 | 上記以外のパッチ・マイナー更新。GitHub Actions のパッチ・マイナー更新も含む | 省略してよい | CI で検証でき、影響が限られるため |

- 行1は例示ではなく分類基準でもある。Spring Security は対象。将来導入を承認した場合の PostgreSQL イメージ、Flyway、JDBC ドライバー、TOTP・QR 生成等も、その認証・暗号・トークン・DB への関与に基づいて対象とする。
- 列挙にない依存も関与があれば行1とする。依存追加時は、この分類も確認する。
- 行3で省略する場合も、CI の全ジョブの成功を確認し、人が依存名と変更前後のバージョンの差分を見てマージする。CI 設定の存在だけで成功と扱わず、対象 PR の実行結果で判定する。
- 例外は Dependabot が作った変更そのままの PR に限る。人や AI が追従修正のコミットを追加したら、通常の PR として扱い、レビューを受ける。
- Dependabot の PR では、[PR テンプレート](../.github/pull_request_template.md)の通常の AI レビュー欄は使わない。ただし、必須レビューの実施結果や、省略時の適用行・CI・人の確認は PR 上に記録する。
- CI が失敗している PR は、原因が分かるまでマージしない。行3による省略・マージには全ジョブの成功が必要。
- リリースノートに破壊的変更があるなど、判断に迷う更新は行2として扱う。行1に該当する場合は行1を優先する。
- Maven 本体の更新はチェックサムの更新も必要なため、Dependabot の PR ではなく手動で行う。[固定・チェックサム検証手順](development.md)に従う。
- 手動の Maven 更新は通常の PR として独立レビューを受ける。Maven Wrapper 自体の Dependabot 更新も行1によりレビュー必須。
