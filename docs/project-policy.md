# プロジェクト方針・設計

## 1. 目的と対象範囲

このプロジェクトは、Spring Boot と htmx を使うアプリケーション開発のための「動かして学べる日本語サンプル集」です。
業務アプリケーションそのものや、どの業務にも使える共通基盤を作ることは目的にしません。

### 実現すること

- htmx の HTML 属性と、HTTP 通信・サーバー処理・画面更新の関係を理解できる。
- 部分更新でも、入力エラー、処理中表示、通信失敗、キーボード操作に対応する。
- DB を用意せず、初期データで何度でも試せる。
- 公式例を Spring Boot 向けに組み立て、日本語解説と確認手順を付ける。
- 各例について、できること・制約・本番利用時の注意点を説明する。

### 当初の対象外

- DB、ORM、マイグレーション、外部 API、コンテナーを必須とする実行環境
- 本番公開のためのインフラ、監視、認証・認可の完成形
- React などの SPA フレームワーク、Node.js を前提にしたビルド
- 追加ライブラリが必要な公式例の完全再現
- SSE / WebSocket などの拡張機能の先行導入（C05 の htmx SSE 拡張は個別合意済みの例外。WebSocket は引き続き対象外）

対象外は永久に禁止という意味ではありません。学習上の必要が生じた場合に、理由と影響を確認してから変更します。

## 3. 基本の処理モデル

```text
利用者の操作
  -> HTML の hx-* 属性を htmx が読み取る
  -> 同一オリジンの Spring MVC に HTTP リクエスト
  -> Controller が入力を受け取り、必要な処理を呼ぶ
  -> Thymeleaf が HTML 全体または断片を生成
  -> htmx が指定された部分を更新
```

「HTML 断片」は、一覧の行や編集フォームなど、ページの一部分に使う HTML のことです。
基本は JSON を JavaScript で HTML に組み立て直すのではなく、サーバーが生成した HTML を返します。

### 推奨する最小構成

初期実装は以下の構成です。Java のベースパッケージは `com.example.htmx` です。

```text
プロジェクトルート
├─ pom.xml
├─ mvnw
├─ mvnw.cmd
├─ .mvn
│  └─ wrapper
├─ README.md
├─ docs
├─ src
│  ├─ main
│  │  ├─ java
│  │  │  └─ com.example.htmx
│  │  │     ├─ SampleApplication.java
│  │  │     ├─ config
│  │  │     └─ examples
│  │  │        └─ clicktoedit
│  │  └─ resources
│  │     ├─ application.properties
│  │     ├─ templates
│  │     │  └─ examples
│  │     └─ static
│  │        ├─ css
│  │        ├─ js
│  │        └─ vendor
│  └─ test
│     └─ java
```

- Java はサンプル単位でまとめ、学習時に関連処理を追いやすくする。
- Controller は HTTP 入出力、フォームは入力値と制約、必要なサービスは状態操作を担当する。
- 状態や処理がない例まで、形式的に Service / Repository / Interface を作らない。
- HTML はページ全体と差し替え用の Thymeleaf フラグメントを使い分ける。
- 共通化はヘッダー、ナビゲーション、エラー表示、セキュリティ連携など必要な部分に限る。

### URL と応答

- 学習用ページは `/examples/{slug}` を基本にする。
- 断片の取得・更新 URL はサンプル配下に置き、通信表で公開する。
- 通常のページ URL に直接アクセスしても、ページ全体を表示できる。
- 同じ URL が全体と断片を返し分ける場合は `HX-Request` を使い、必要な `Vary` ヘッダーも扱う。
- `HX-Request` は表示の選択にだけ使う。認可・CSRF 検証を省略する条件にはしない。
- 更新は POST / PUT / PATCH / DELETE 等の適切なメソッドで行い、GET で業務データを変更しない。
- 標準フォームで代替可能な操作は、その導線も残す。htmx 専用の操作には制約を表示する。

## 4. 依存ライブラリの方針

| 用途 | 方針 |
| --- | --- |
| HTTP / MVC | Spring Boot の MVC 向け公式 starter |
| HTML 生成 | Thymeleaf 向け公式 starter |
| 入力検証 | Bean Validation 向け公式 starter |
| セキュリティ | Spring Security 向け公式 starter |
| テスト | Spring Boot のテスト支援、Spring Security のテスト支援 |
| 部分更新 | htmx の固定バージョンの配布ファイル |
| UI | 標準 HTML、独自の小規模 CSS、必要最小限の JavaScript |

starter の正確な artifactId は、採用する Spring Boot 4 の公式ドキュメントと生成結果で確認します。
Spring 関連の依存は原則として Spring Boot の依存管理に従い、個別のバージョン上書きを避けます。

- npm、WebJars、CSS フレームワーク、追加の htmx 拡張は初期必須にしない。
- htmx は公式配布元・バージョン・取得日・整合性確認方法・ライセンスを記録する。
- 実行時に CDN へ依存しない。初回の JDK・Maven・依存取得までオフラインで行えることは保証しない。
- 新しい依存は、標準機能で実現できない理由、保守状況、ライセンス、更新負担を説明して採否を決める。
- Spring Boot、JDK、htmx とその推移的依存も更新確認の対象にする。依存削減と更新管理を両立する。

## 5. DB を使わないデータ管理

- 検索・一覧表示は架空の固定データを使う。実在する個人情報や秘密情報を置かない。
- 編集・削除などの可変データは、原則として HTTP セッション単位で分離する。
- 可変の一覧を singleton の共有フィールドに置き、利用者間で意図せず共有しない。
- 初期値から状態を作る際は、可変オブジェクトまで独立させる。
- 同じセッションからの並行更新も想定し、必要な排他・スナップショット生成を行う。
- 初期状態に戻す操作は CSRF 対象の更新リクエストにする。
- 再起動・セッション失効でデータは消える。HTTP セッションの有効期限を設定し、画面でも説明する。
- 件数、文字数、アップロードサイズ、ジョブ数・実行時間などに上限を設け、具体値を各例に記録する。
- ポーリングの GET は状態の参照だけを行い、ジョブ開始・キャンセルは更新リクエストで行う。
- 一時ファイルやバックグラウンド処理は成功・失敗・キャンセル・失効時の後始末を設計する。

DB の代わりにメモリへ移すだけでは、競合やリソース枯渇の問題は解決しません。
学習用として簡略化する箇所は、実装と説明の両方に明記します。

## 6. セキュリティの基準

### ローカル利用と認証

- 当初はログインを設けず、サンプル画面へのアクセスを許可する設定を明示する。
- Spring Security のデフォルトの生成パスワード・ログイン画面に任せない。
- CSRF、出力エスケープ、基本的な保護ヘッダーを、認証なしという理由で無効化しない。
- 外部公開・LAN 共有に設定を変える前に、認証・認可・HTTPS・負荷対策を別途検討する。

### CSRF

CSRF は、利用者のブラウザーに意図しない更新リクエストを送らせる攻撃です。

- Spring Security の CSRF 対策を有効にする。
- 通常フォームには Thymeleaf と Spring Security の連携でトークンを含める。
- htmx による POST / PUT / PATCH / DELETE にも、サーバーが公開したトークンとヘッダー名を使って送信する。
- 連携コードは共通の外部 JavaScript にまとめ、同一オリジンへの送信だけを対象にする。
- サーバー側のトークン検証を維持し、トークン欠落・不一致は 403 にする。
- 403 が画面に分かる形で表示され、セッション失効時は再読み込みなどの復帰方法を案内する。
- 実装時に採用バージョンの CSRF トークン処理と照合し、全更新メソッドで正しい送信と拒否を確認する。

### 入力・HTML・スクリプト

- サーバー側で文字数、値の範囲、選択肢、対象 ID の存在を検証する。
- クライアント検証は補助とし、JavaScript や HTML の制約を外した入力も検証する。
- 利用者入力は Thymeleaf のエスケープを使い、未加工 HTML として挿入しない。
- 断片に実行用の script タグを含めない。補助 JavaScript は同一オリジンの外部ファイルに置く。
- htmx の `selfRequestsOnly: true`、`allowScriptTags: false`、`allowEval: false` を基本とする。
- `allowEval: false` により使えなくなるトリガー条件式、`js:` 式などは、標準 JavaScript のイベント処理で代替するか、その例を参考扱いにする。
- CSP を設定し、`unsafe-inline` / `unsafe-eval` に安易に依存しない。htmx の注入スタイルを使わない場合は `includeIndicatorStyles: false` とローカル CSS を組み合わせる。
- 採用する CSP と全サンプルの整合性は、ブラウザーのコンソールでも確認する。
- 利用者入力や CSRF トークンを、JavaScript 文字列への連結やログ出力に流用しない。

### ファイル・例外

- アップロードは容量・件数・形式を検証し、ファイル名やブラウザー申告の MIME 型だけで安全と判断しない。
- 利用者のファイル名を保存パスに使わず、公開ディレクトリに保存しない。
- プレビュー、実行、恒久保存は初期要件に含めない。一時保持するなら保持期限と削除を実装する。
- 予期しない例外はサーバー側に記録し、画面にはスタックトレースや内部情報を出さない。
- エラーを握りつぶしたり、更新失敗時に成功通知を返したりしない。

## 7. UI とエラー応答

- 共通の見出し・ナビゲーション・説明配置を使い、装飾目的の依存追加を避ける。
- 入力にラベルを付け、エラーと入力欄を関連付ける。状態を色だけで表現しない。
- 処理中表示、送信ボタンの無効化、二重送信対策を必要な操作に付ける。
- サーバー側でも更新の整合性を守る。ボタンの無効化だけを安全策としない。
- 差し替え後のフォーカス、キーボード操作、必要な `aria-live` 通知を確認する。
- アニメーションは動きを減らす設定に配慮し、自動読み込みには手動操作の代替を用意する。

| 場面 | 基本方針 |
| --- | --- |
| 正常表示・更新 | 200 と用途に合った HTML。削除も空の HTML 等、採用する swap と整合させる |
| 入力エラー | 422 と、入力値・項目別エラーを含むフォーム断片 |
| 不正な要求 | 400。理由と修正可能な操作を案内 |
| 対象なし | 404。画面全体でも断片要求でも利用者へ通知 |
| CSRF エラー | 403。成功として扱わず、再読み込み等の案内 |
| 競合を扱う例 | 409。状態の再取得や再操作を案内 |
| 一時的な容量上限 | 503。回復条件と既存データを保つ方法を案内 |
| 予期しない失敗 | 500。共通のエラー表示とサーバーログ |
| 通信断・タイムアウト | HTTP 応答とは別に検知し、入力を残して再試行を案内 |

htmx は標準設定で多くの 4xx / 5xx 応答を画面へ差し替えません。
**422 の想定した HTML 断片だけを差し替える設定と、それ以外の共通エラー通知を明示的に実装します。**
エラー応答を無条件に差し替えたり、ステータスを 200 に偽装して回避したりしません。

## 8. 変更・実装の進め方

サンプルを一つずつ、実装・解説・テストをそろえて追加します。
最初の一例で共通構成を検証し、必要な範囲だけを共通化します。
方針変更時は本書、サンプル台帳、利用者向け説明を同時に更新します。

PR 作成前には、[レビュー方針](review-policy.md) に従い、実装コンテキストとは別のサブエージェントで最新差分を1回以上レビューします。
実装セッションでの動作確認・テストは継続しますが、独立したレビューの代わりにはしません。
P1 の保留・指摘の棄却とマージ承認は人が判断します。P2 の受け入れはレビュー方針に定める評価と理由記録に従います。Dependabot の例外と、未整備のレビュー基盤も同方針に記載します。
依存追加時は採否の理由を ADR（設計判断記録）として残します。[初期依存の ADR](adr/0001-initial-stack.md) を導入前に作成しています。

ライセンス未定の段階で、このプロジェクトに任意の OSS ライセンスを付けません。
第三者のコード・画像等を取り込む場合は、出典とライセンス・再配布条件を確認し、必要な表示を残します。
