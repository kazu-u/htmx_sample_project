## ブラウザー確認

VS Code統合ChromiumとPlaywright操作で確認。検証サーバー18080と、htmx要求を600ms遅延させる一時ローカルHTTPプロキシ18081を使用。両方停止済みで、依存やアプリへのプロキシ追加はしていない。

| 操作 | 結果 |
| --- | --- |
| 「佐」→100ms後「佐藤」と連続入力 | 最後の入力から300msでは要求0件、約515ms後に1件のみ。「佐藤」1件、入力DOMと値・フォーカスを保持 |
| 「該当なし」入力直後にEnter | 0件を表示。さらに650ms待っても追加要求なし |
| 空欄、SATO、EXAMPLE.COM、検索ボタン | 全8件、1件、全8件を表示。英字大小を区別せず手動検索可能 |
| compositionstart/input(isComposing)後650ms待機しEnter・検索ボタン | 要求0件。compositionendと最後のinput後に「開発」を1件だけ検索。実OSのIME操作ではなく合成イベントによる確認 |
| maxlengthを外して61文字送信 | 422の結果領域と項目エラーを表示。入力61文字を保持しaria-invalid=true。修正後は正常検索・falseに戻る |
| プロキシ経由で進行中の検索中に条件を変更 | 古い要求はstatus0で中断し最新要求を送信。最新結果だけを差し替え、入力フォーカス保持、busy解除 |
| 旧要求の送信350ms後に新入力、さらに350ms待機 | 新要求送信前に届く旧200も旧422も差し替えなし。新入力と直前の結果を保持し、その後最新結果を表示 |
| 別値へ変更して元の検索語へ戻す | 値が同じでも旧応答は抑止。新しい要求の結果だけを反映 |
| 検索URLを接続失敗にする | 共通エラーと検索未完了を通知し入力・前回結果保持、busy解除。同じ条件のまま検索ボタンで回復 |
| 503をブラウザー側で模擬 | 共通通知、未完了案内、前回結果保持。503を成功結果へ差し替えない |
| プロキシ経由でブラウザー内のtimeoutを100msに短縮 | 検索タイムアウトと再試行案内を通知、入力・前回結果保持、busy解除。10秒へ戻し同じ条件で再検索成功。通常設定は10秒のまま |
| 390px幅・reduced-motion | 横スクロールなし（viewport390 / scrollWidth375）。全8件の表・ラベル・通知を確認 |
| 条件を空に戻す | GETで空欄・全8件に戻る |
| htmxとアプリのスクリプトをブラウザーで遮断 | 通常フォームがGETで検索し、URLにqueryのみを送り、1件表示と入力を保持。戻るで全8件、進むで1件。完全なJavaScript無効化とは区別する |
| 既存サンプルの422回帰 | Inline Validation の不正→正常メールと名前未入力の全体422、Click to Edit・Edit Row の422入力保持とフォーカスが動作 |
