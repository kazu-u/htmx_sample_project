# File Upload 検証記録

## 対象

- 要件: F-01、F-04、F-06〜F-09、F-22
- 検証日: 2026-10-31
- 対象: UTF-8 の `.txt` ファイルを1件送信し、サーバー側で形式・容量を検証する。ファイル本体は保存・表示せず、通信の送信進捗とサーバー処理の進捗を区別する。

## サーバー側検証

環境: Windows、Java 25.0.2、Spring Boot 4.1.2、Maven Wrapper 3.9.16、組み込み Tomcat 11.0.27。

| コマンド | 結果 |
| --- | --- |
| `.\mvnw.cmd --batch-mode clean '-Dtest=FileUploadTests' '-Dsurefire.failIfNoSpecifiedTests=true' test` | 成功。専用11テスト、失敗・エラー・スキップなし |
| `.\mvnw.cmd --batch-mode clean verify` | 成功。全170テスト、失敗・エラー・スキップなし |
| `git diff --check` | 成功。空白エラーなし |
| GitHub Actions `test`（[#20](https://github.com/kazu-u/htmx_sample_project/pull/20)） | 失敗。GitHub が「最近の支払い失敗または利用上限」を理由に runner 起動前に終了し、テストは実行されず。ローカルテスト結果とは区別する |

専用テストは通常フォームと htmx、CSRF、UTF-8・拡張子・ファイル名の検証、ファイルサイズ境界を確認します。実 Tomcat ではフォーム本文の CSRF トークンによる通常送信・不正トークン拒否・上限超過も確認します。1 MiBちょうどを受理し、超過を413で返すこと、および成功・413双方の要求後にサーブレット一時領域のファイルが残らないことも確認します。

## 実ブラウザー確認

環境: VS Code 統合ブラウザー（Chromium 系。正確なエンジンの版は確認手段から取得できず）、画面幅390 px。実際のサンプルページを使用。

| 操作 | 結果 |
| --- | --- |
| 800 KiBの UTF-8 テキストを送信 | 16 KiB単位の複数回の送信進捗イベントを表示。成功結果を通知し、送信成功後にファイル選択をクリア |
| 形式不正のファイルを送信 | 422のエラーを通知し、選択ファイルを保持。ファイル入力欄へフォーカスを戻す |
| 1 MiBを超えるファイルを送信 | 413の上限エラーを通知し、選択ファイルを保持 |
| 画面幅390 px | ページの横スクロールなし |

## 制約・未確認事項

- ブラウザーの進捗はブラウザーからサーバーへの転送量で、サーバーの検証処理の進捗ではありません。
- Firefox等の別ブラウザー、モバイル実機、画面読み上げソフト、JavaScript無効時の実ブラウザー操作は未確認です。通常フォームの送信・エラー応答はサーバーテストで確認しています。
- 手動で選択した日本語以外のファイル名について、実ブラウザーのファイル選択・表示は未確認です。
- 追加依存はありません。アップロード内容の表示・プレビュー・実行・恒久保存は行いません。

## 独立レビュー

- 第1回レビューで、追加フィールドのファイルを含む件数検証、通常 multipart フォームの本文 CSRF 経路、フォーカス動作の記録について指摘を受けました。
- 3点を修正し、別フィールド名を含む複数ファイルの拒否、組み込み Tomcat でのフォーム本文 CSRF の成功・拒否・413、フォーカス記録を確認しました。
- 第2回レビューで、応答受信イベントを送信進捗として扱う可能性を指摘されました。`xhr.upload` の進捗だけを表示するよう変更し、実ブラウザーで送信中の進捗・成功・入力クリアを再確認しました。
- 第3回レビューで画面説明・台帳の進捗イベント名が実装と異なると指摘され、対象 XHR の `upload` に標準 `progress` リスナーを登録する方式と公式例との差分を説明に反映しました。
- 第4回レビューでは指摘はありませんでした。
